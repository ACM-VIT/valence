# Problem package format (v0)

A problem package is a directory that holds everything Valence needs to show,
judge and test one problem. Packages live in the repo under `problems/` and are
imported into the database by tooling; this document is the contract between
the two.

```text
<slug>/
  problem.yaml      # metadata and limits
  statement.md      # the problem statement
  tests/            # numbered input/output pairs
    01.in
    01.out
    ...
  solutions/        # optional: reference and intentionally wrong solutions
    ac-main.cpp
    wa-int-overflow.cpp
    ...
```

The directory name should match `slug`.

## problem.yaml

```yaml
version: 0
slug: aplusb
title: "A + B"
time_limit_ms: 1000
memory_limit_mb: 256
checker: tokens
samples: [1, 2]
```

| Key | Required | Rule | Default |
| --- | --- | --- | --- |
| `version` | yes | Must be `0`. | |
| `slug` | yes | Matches `^[a-z0-9][a-z0-9-]{1,63}$` (2 to 64 chars, lowercase letters, digits and `-`, not starting with `-`). Unique across all problems. | |
| `title` | yes | 1 to 200 characters. | |
| `time_limit_ms` | no | Integer, 100 to 20000. Per test, wall clock of the solution process. | `1000` |
| `memory_limit_mb` | no | Integer, 16 to 2048. Stored as KiB (`memory_limit_mb * 1024`), so 16384 to 2097152 KiB. | `256` |
| `checker` | no | `exact`, `tokens` or `float:EPS`. `custom` is reserved for V-219 and rejected in v0. | `tokens` |
| `samples` | no | List of test numbers shown on the problem page. Each must name an existing test; no duplicates. | `[]` |

Unknown keys are errors. A misspelled `time_limt_ms` should fail the import,
not quietly fall back to the default.

These limits mirror the `CHECK` constraints on the `problems` table in
`db/migrations/00001_init.sql`. If one side changes, change the other.

The same rules are in `docs/problem.schema.json` (JSON Schema). Start each
`problem.yaml` with a modeline pointing at it, so editors validate the file
against Valence's schema instead of guessing one from the file name:

```yaml
# yaml-language-server: $schema=../../../docs/problem.schema.json
```

The schema cannot check that `samples` names tests that exist; the importer
does that.

### Checkers

- `exact`: the output must equal the expected output byte for byte.
- `tokens`: both outputs are split on whitespace (spaces, tabs, newlines) and
  the token lists must be equal. Extra blank lines and trailing spaces do not
  matter. This is the default because it is what most problems want.
- `float:EPS`: like `tokens`, but a pair of tokens that both parse as numbers
  matches when the absolute or relative difference is at most `EPS`. `EPS` is
  a plain decimal or exponent number, matching
  `[0-9]+(\.[0-9]+)?([eE][-+]?[0-9]+)?`: `float:1e-6` and `float:0.000001` are
  valid, `float:.001` and `float:-1e-6` are not.

## statement.md

The statement is [CommonMark](https://commonmark.org/) with
[KaTeX](https://katex.org/) math: `$...$` inline and `$$...$$` for display
math. It must be valid UTF-8 and at most 256 KiB (262144 bytes).

Recommended sections, in order: the story or task, `## Input`, `## Output`,
`## Constraints`, and optionally `## Notes`.

Do not paste sample tests into the statement. The problem page renders the
tests listed in `samples` itself, so they can never drift out of sync with the
real test data.

## tests/

- Tests come in pairs: `NN.in` and `NN.out`.
- Numbering starts at `01` with no gaps (`01`, `02`, `03`, ...). Use two digits
  for up to 99 tests and three digits beyond that; all files in a package use
  the same width.
- Every `.in` has a matching `.out` and vice versa.
- Files are UTF-8 with `\n` line endings (no `\r\n`) and end with a newline.
- Each file is at most 64 MiB.
- `.out` files are generated by running a correct solution on the `.in` file,
  never typed by hand.

Test files are marked `-text` in `.gitattributes`, so git never rewrites their
line endings. They are stored byte-exact, which matters for the `exact`
checker.

## solutions/

Optional, but every package should have at least one accepted solution, and
the packages in this repo also carry wrong ones so the judge can be tested
against known verdicts.

Files are named `<verdict>-<name>.<ext>`:

- `verdict` is the verdict the solution is expected to get on the full test
  set: `ac`, `wa`, `tle`, `mle`, `re`, `ole` or `ce`.
- `name` is a short lowercase description, e.g. `int-overflow`.
- `ext` picks the language: `.cpp` is C++17, `.py` is Python 3.

The expected verdict is the first failing test's verdict, the same way the
judge reports it. A `wa-` solution may pass some tests, but it must not get
any verdict other than WA or AC on any test.

## Room to grow

v0 is deliberately small. These come with version 1 or later, behind a new
`version` value so old packages keep importing unchanged:

- **Test groups** (subtasks with their own points).
- **Generators** (V-602): tests produced by a program instead of committed
  files, for large or randomized data.
- **Interactive problems**, where the solution talks to a judge program.
- **Custom checkers** (V-219): `checker: custom` with a checker program in the
  package, for problems with many correct answers.

## Worked example: A + B

The full package is in `problems/examples/aplusb`.

```text
problems/examples/aplusb/
  problem.yaml
  statement.md
  tests/
    01.in  01.out    # 1 2                     -> 3
    02.in  02.out    # -5 3                    -> -2
    03.in  03.out    # 0 0                     -> 0
    04.in  04.out    # 2000000000 2000000000   -> 4000000000
    05.in  05.out    # -1000000000 -1000000000 -> -2000000000
  solutions/
    ac-main.cpp
    ac-main.py
    wa-int-overflow.cpp
    tle-busy-loop.py
    mle-big-vector.cpp
    re-divide-by-zero.py
    ole-flood.py
    ce-missing-semicolon.cpp
```

`problem.yaml`:

```yaml
# yaml-language-server: $schema=../../../docs/problem.schema.json
version: 0
slug: aplusb
title: "A + B"
time_limit_ms: 1000
memory_limit_mb: 256
checker: tokens
samples: [1, 2]
```

The constraints are $-2 \cdot 10^9 \le a, b \le 2 \cdot 10^9$. Each input
fits in a 32-bit `int` (max 2147483647), but the sum does not, which is the
trap this problem sets.

Tests 01 and 02 are the samples shown on the page. Test 04 is the one that
matters: `2000000000 + 2000000000 = 4000000000` overflows `int`, so
`wa-int-overflow.cpp` passes 01 to 03 and 05 and fails 04. The `.out` files
were generated with `python3 solutions/ac-main.py`, and both `ac-` solutions
agree on all five.
